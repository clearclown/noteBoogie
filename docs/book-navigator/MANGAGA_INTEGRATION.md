# noteBoogieからmangagaへ蔵書と読書記録を提供する要件

参照契約: **NBMG-20261003 / v0.1**。提供側要件の改訂: 2026-10-03 / 第2稿。実装調査の基準: noteBoogie `d8bfac4b7afe5b40b9413677655432f081bc39e8`。

この文書は[PMVV](PMVV.md)を具体化した、実装前の提供側要件である。**noteBoogieは原本・本文・出典・読書記録の管理とAI処理を、mangagaはiPhoneでの日常の読書を担う。** 本ID・版・原本位置を共有し、取り込みから持ち出し、記録の書き戻し、後日の参照までをつなげる。製品方針は[PDR-003](../7-DEVELOPMENT/decisions/PDR-003-personal-library-and-mangaga.md)に記録する。

以下は到達要件であり、実装完了を示さない。調査基準時点のmangagaには前処理JSONを読み込む開発版があるが、noteBoogieの蔵書APIや質問・音声APIとは未接続である。

共通契約は姉妹リポジトリの[統合要件](../../../mangaga/docs/noteboogie-integration-requirements.md)、受け取り側は[mangaga仕様](../../../mangaga/specs/ios/noteboogie.spec.md)を参照する。本書の第2稿は通信契約の版更新ではない。[契約補足](MANGAGA_CONTRACT_ADDENDUM.md)を両側で採用し、契約版・Schema・共通テストデータ（fixture）を揃えるまで、追加フィールドをv0.1として送信しない。姉妹チェックアウトがなければ、契約IDで同じ版を取得する。

本文はNB-01〜10の機能要件、[受入計画](MANGAGA_ACCEPTANCE.md)は段階別の完成条件を定める。ルートの同名ファイルは本書への入口とする。

## 引き継ぐ前提と今回の範囲

初期対象は一人の所有者の書庫である。PC上で原文をOCR・AI処理し、mangagaへ渡すときは既存Rustの暗号化処理を使う構成を推奨する。SaaS化・多利用者化は行わず、既存の[PMVV](PMVV.md)の方向を維持する。

初回はPDFの読書・RSVP・暗号化した取得と記録の往復を完成させる。質問・章音声・回答履歴は後続の段階Dの必須要件とする。EPUBの直接取り込み、音声での質問入力、単語単位の音声同期は後続の検討対象。入力形式の扱いは[受入計画](MANGAGA_ACCEPTANCE.md)に定める。PCで原文を処理する構成を採り、無人運用の鍵保管方法は実装前に確定する。

モデル選択と外部への送信方針はnoteBoogieに集約する。mangaga用に別のLLM設定画面や直接のプロバイダー接続を増やさない。既存のモデル設定は保持するが、新しい連携経路では外部送信の可否を明示し、未設定時にクラウドへ自動的に切り替えない。

## NB-01: 原本と読書用本文を別に保存する

本ごとに安定した`book_id`を発行し、既存の`source_id`、`notebook_id`、`audiobook_id`を対応付ける。原本差し替えで`content_revision`、再OCR・注記補正で`reading_revision`を更新する。改名ではIDを変えず、同名別書籍は別IDにする。同じ原本を再投入したときの重複判定はハッシュと利用者の意図で決める。

次の生成物を分けて保存する。

- 原本PDF/EPUB等。元のバイト列を変更しない。
- OCR原文とレイアウト情報。失敗・空白・未処理ページも区別する。
- 本文・章・注記・ルビ・図表の役割と読み順。原本へ戻れる位置を持つ。
- 要約、図のAI説明、音声台本、生成音声。生成物であることを明示する。

既存の音声向け`Source.full_text`を読書原文と見なして移行しない。元のOCRデータが残っていればそこから作る。残っていなければ原本の再処理が必要な本として表示し、一括で無断再生成しない。既存音声・メモ・質問履歴を削除して移行しない。

**完了条件:** 同名別書籍、改名、同一原本の再投入、原本差し替え、再OCRのテストで、ID・版・元データが期待どおり保たれる。既存DBからの移行・復元試験が通る。

## NB-02: 本文処理は原本位置と読み順を保持する

共通契約CT-02に従い、各ブロックにID、原文、役割、読み順、物理ページ、位置矩形、縦横方向、章への所属を持たせる。矩形は表示上のcrop boxを基準に、左上原点の正規化座標とする。印刷上のページ表記は別に保持する。

ブロック内の文字位置、範囲の終端、文字正規化は[契約補足C-01](MANGAGA_CONTRACT_ADDENDUM.md#c-01-同じ文字位置を指す)で固定する。再OCRの旧新対応が不明なら、同じIDや位置を推測で流用しない。

文字付きPDFと画像PDFの経路を分け、縦書き・横書き・日英混在・段組みを扱う。日本語のルビ、上部の柱、下部のページ番号、小さな注記、本文中の数字、図表・数式を区別する。変換器が矩形や列順を出せない場合は不足能力として明示する。Markdownから正確な座標を捏造しない。変換器の改修が必要なら、その入力/出力と再現例を別課題にする。

LLMの役割はブロックの分類と構造候補の提示に限定する。返せるのは既存IDへの役割・関係・順序候補とし、置換本文を原文として採用しない。未知ID、欠落、重複、全本文の除外、構造矛盾を検出する。削除候補も原文から消さず、分類前後を戻せるようにする。

全ページを一つの文字列として扱うだけでは、段落途中の脚注・縦書きのルビを修復できない。現在のmangaga側のページ別Markdown入力は暫定アダプターであり、完成形のデータモデルにしない。

**完了条件:** 合成fixtureで原文の意図しない書き換え0件、IDの欠落・重複0件。縦書きと日英混在の実書籍を原本と照合し、抽出精度と分類精度を別々に報告する。具体的な受入値案は共通要件末尾を参照する。

## NB-03: Webで処理結果を確認・修正する

原本と読書用本文を並べて確認できる画面を用意する。ページの欠落、読み順の不確かさ、除外した柱・注記、章境界を示し、役割・順序・章境界を修正できるようにする。AI補正文を作る場合も原文と別版にし、通常の本文と混ぜない。

本の状態は、取り込み中、OCR中、本文確認待ち、原本のみ利用可、読書用本文あり、音声生成中などに分ける。要約やTTSが失敗しても原本・本文を読める。修正結果は版として公開し、mangagaが更新を取得できるようにする。

検出したページ欠落・重大な読み順の疑いは読書版の公開を止める。元の完成版か原本表示は利用可能とする。機械検査済みと人による確認済みを分け、確認範囲・検査版・残る問題を記録する。表・数式の平文化が不確かな場合は、欠落扱いで捨てず原本へ戻す。判定条件は[受入計画](MANGAGA_ACCEPTANCE.md)に従う。

利用者がOCRの誤字を直す場合も、OCR原文を上書きしない。修正者、変更箇所、理由、元の版を残し、修正本文を新しい読書版にする。修正本文からも原本を開けるようにする。

**完了条件:** ページ番号の誤除外をWebで戻す→新しい読書版を発行する→旧版も保持される、という試験が通る。モデルのエラーと読書可否が別に表示される。

## NB-04: ジョブと公開通知を再起動可能にする

既存のimportジョブを、段階・入力版・実行設定・出力版・再試行状態を保存する処理へ拡張する。OCR、本文構造、埋め込み、要約、音声の依存関係を明示し、不要な全工程の再実行を避ける。処理済みページ数が分かるときだけ進捗率を返す。

本文修正時は、影響を受ける検索索引・要約・台本・音声と再処理費用を示す。旧生成物には入力版を表示し、新版用と取り違えない。保存済み回答を再計算で上書きせず、その時点の引用と版を残す。未完成の索引を新版の検索に混ぜない。

PCフォルダ監視は初回完成後の新規機能として扱う。登録したフォルダだけを対象にし、書き込み完了後に検証して取り込む。ファイル名の変更や一時的な未接続を原本削除と誤認しない。Webからの取り込みと同じ本ID・重複判定を使う。

公開通知はDBなどへ永続化し、配信用アダプターが受領したことを確認するまで再送可能にする。プロセス内の一時タスクだけで発行を保証しない。同じ本・版・処理の再送で、重複登録や意図しないLLM/TTSの追加消費を起こさない。旧完成版は新しい版の検証完了まで有効にする。

**完了条件:** PC/worker停止、モデル未設定、変換器不在、OCR途中失敗、通知後の応答喪失、重複通知から復帰する。完成していない版がmangagaへ公開されない。

## NB-05: 読書用成果物のAPIとfixtureを提供する

noteBoogieは、原本・読書本文・構造・生成物を提供するサービス層と内部APIを持つ。公開側はmangagaの認証・配信アダプターを通す。共通契約CT-04の外部APIをiPhoneの入口とし、noteBoogieの内部URLや絶対ファイルパスを配信用URLとして返さない。

最初の成果物として、次を提出する。

1. 本一覧、能力、ジョブ状態、版別manifest、生成物取得のOpenAPIとJSON Schema。
2. 本ID・原本ハッシュ・読書版・原本位置を持つ公開fixture。私的な書籍全文をコミットしない。
3. 縦書き、日英混在、画像PDF、本文未完成、別原本のハッシュ、不明な契約版の成功/失敗例。
4. パッケージ公開・削除・版変更を通知する永続イベント形式と再送・受領仕様。

内部APIの推奨名前空間は`/api/integrations/mangaga/v1`。これは実装前の提案であり、既存ルートを意味しない。外部`/api/reader/v1`への対応表と認証方式を固定してからクライアントへ渡す。サービス層を再利用し、同じ本文を別経路で異なる処理にしない。

本文を変えずに音声を追加した場合も公開パッケージを一意に識別する。原本のみ利用可と本文付きでは必須生成物を区別し、取得中の旧版を変更しない。具体案は[契約補足C-02](MANGAGA_CONTRACT_ADDENDUM.md#c-02-公開パッケージを固定する)を両側で採用する際に確定する。

**完了条件:** mangaga側のSwift/Rustで同じfixtureを検証できる。mockだけでなく実FastAPIと実DBを経由した取得試験が通る。音声は任意生成物として扱い、読書用の必須生成物を妨げない。

## NB-06: 質問と音声を原本へ結び付ける

質問は本ID・版・章/ブロック範囲を入力に持ち、サーバー側で所属を照合する。既存Source/章質問を再利用しつつ、根拠を読書原文へ結び直す。生成した図の説明や台本を引用する場合は、原文の引用と区別する。根拠が見つからないときは回答不能を返す。蔵書全体のmentorへ黙って範囲を広げない。

引用は原文のブロックとページへ戻れる形式で返す。既存の引用一致判定を残し、引用が回答を支えているかは別の品質評価を行う。長い本を黙って切り詰めて回答する処理を作らない。

音声は音声生成物ID、入力版、章、種別、ハッシュ、サイズ、MIMEを持つ。既存のメンターによる語りは音声解説と明示し、原文朗読と区別する。mangagaは章単位で取得してオフライン再生するため、原本と同じ大きな一括アーカイブだけを提供する方式にしない。

質問を開いた時点の本・版・章と音声ID・秒数を保持する。引用を開いても質問範囲を勝手に変えず、明示した再開操作で同じ音声の停止位置に戻す。再生成済みなら旧音声を使うか、新しい章頭から再開するかを選べるようにする。PC切断時は質問を暗号化した下書きとして保存し、再接続後も自動送信しない。背景再生とVaultロックは[受入計画](MANGAGA_ACCEPTANCE.md)の実機試験を必須とする。

**完了条件:** 本・章の所属不一致や未提供の版への要求を拒否する。保管済み旧版への明示した質問は、その版の本文で検証する。引用から同じ原本の箇所を開ける。音声失敗時にも本文が読め、再生成された音声へ旧音声の再生位置を誤適用しない。

## NB-07: 読書記録をWebとiPhoneで共有する

CT-05のイベント形式で、本の位置・しおり・注釈を受け取り、差分取得できるようにする。音声の再開位置は既存ブラウザ保存から移行できるようにする。現在のブラウザlocalStorageやmangagaの端末位置保存をサーバー同期済みと扱わない。

書き戻しの暗号化・復号とWebへの反映の責任は[契約補足C-04](MANGAGA_CONTRACT_ADDENDUM.md#c-04-認証と復号の担当を固定する)に定める。段階Dで追加する質問履歴はNB-09として扱い、単なる読書位置イベントに本文を詰め込まない。

追加イベントは統合する。同じ注釈の同時編集、異なる再開位置、原本差し替えでアンカーが移せない場合は、利用者の記録を無条件で捨てない。削除の記録を保持し、古い端末から削除済みデータが復活することを防ぐ。

**完了条件:** iPhoneのオフライン記録→再接続→Web表示、Webの変更→iPhone取得、重複再送、端末時計のずれ、同時編集、原本再処理、削除競合を検証する。

## NB-08: PC・Tailscale・鍵の責任範囲を守る

PCはAI処理のために原文を扱う信頼済みの場所であり、DB・OCR・埋め込み・音声・会話も保護対象である。同期サーバーや端末に暗号文を保存しても、noteBoogieの実行ホストから原文を隠すことにはならない。

Tailscale内でもアプリ認証を行う。DB、gRPC、worker、gatewayの内部ポートはloopbackまたはコンテナ内部に限定し、認証済みの入口を経由させる。`docker-compose.book.yml`の現在の公開ポート設定を、本番要件を満たした設定だと扱わない。既存のTailscale Serve設定は調査し、他サービスを上書きしない。

初期は一つの所有者・一つの書庫への対応を明示する。mangagaのプロフィール切替をnoteBoogieのユーザー分離に流用しない。APIで要求された本・Source・episode・assetが接続先書庫に属することを確認する。端末失効・未認証・不正なIDを検証する。

Vault暗号化はmangagaの既存Rust APIを使う。noteBoogieに独自暗号やVaultパスフレーズのDB保存を追加しない。配信用アダプターに鍵がないときは待機状態として返す。無人運用の鍵保管方法は、OSの資格情報保管を含めた別の運用設計で決める。端末内専用Vaultを自動でnoteBoogieへ取り込まない。

初回の接続登録、接続先書庫の確認、端末失効、再認証、アダプターから内部APIへの認証を契約に含める。端末の失効で、オフライン端末の取得済みデータまで即時消去できるとは表示しない。

**完了条件:** 未認証、別書庫への参照、パストラバーサル、ログへの本文/秘密値混入、内部ポートへの外部接続、バックアップからの本ID・版・鍵の復元を検証する。外部AIへの送信は処理ごとのポリシーに従う。

## NB-09: 質問と自分の考えを後から参照する

質問・回答・引用・利用者のメモを、本IDと入力版に結び付けて保存する。本の記述、AIの説明、利用者の考えを表示とデータ上で区別する。生成済み回答と利用者の追記は別に持ち、再生成や編集で元の回答を失わない。

Webとmangagaで履歴を取得でき、本・章・語句から探せるようにする。端末での検索は取得済み記録を対象とし、未取得の履歴まで検索できたと表示しない。記録と引用のID・版・出典を保ってJSONと閲覧用Markdownへ書き出す。全文書籍の同梱は別操作にする。取得・同期・削除の契約は[契約補足C-03](MANGAGA_CONTRACT_ADDENDUM.md#c-03-学びの記録を受け渡す)にまとめる。

**完了条件:** iPhoneで章に質問→自分のメモを付ける→Webで検索→同じ版の引用を開く→書き出す、を通す。履歴の通信再送、同時編集、本文再処理、削除後の古い端末の再接続でも記録を取り違えない。

## NB-10: 費用と保存期間を管理できるようにする

本・工程ごとの所要時間、手作業の修正時間、推定/実績費用、原本・版・生成物の容量を区別して記録する。利用者が本数・ページ数・費用・同時実行数の上限を設定できるようにする。未知の費用を0と扱わず、価格不明なら有料工程を待機させる。中断後は完了済み工程から再開し、取消時点までの処理と費用を残す。

保持期間・容量上限・削除対象を設定する。初期設定では原本、利用者の記録、参照されている版を自動削除しない。上限時は新規生成を止め、整理対象を示す。端末から外す操作、サーバーの論理削除、物理削除を区別し、引用の参照先と未同期記録への影響を表示する。削除記録の保持期限と長期オフライン端末の再同期は[契約補足C-05](MANGAGA_CONTRACT_ADDENDUM.md#c-05-削除と再同期を定める)で扱う。

**完了条件:** 予算上限、容量不足、取消・再開、参照中の旧版削除、バックアップ復元を検証する。復元した本ID・版・引用・記録の対応を確認し、運用負担を[受入計画](MANGAGA_ACCEPTANCE.md)に記録する。
