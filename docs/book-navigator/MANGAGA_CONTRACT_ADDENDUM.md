# mangaga共通契約に追加する受け渡し要件

更新日: 2026-10-03。参照契約は **NBMG-20261003 / v0.1**。本書は[提供側要件](MANGAGA_INTEGRATION.md)から生じる次版への提案であり、v0.1の通信仕様を変更したものではない。フィールド名も実装前の候補である。

本書を[共通要件](../../../mangaga/docs/noteboogie-integration-requirements.md)と[mangaga仕様](../../../mangaga/specs/ios/noteboogie.spec.md)へ反映し、契約版・OpenAPI・JSON Schema・fixtureを両側で揃える。採用前に片側だけで送信を始めない。基本の本ID・原本版・読書版はCT-01〜06を引き継ぐ。

## C-01 同じ文字位置を指す

対象: CT-02/05、NB-02/07/09。noteBoogieが位置を発行し、mangagaが同じ箇所を表示する。

位置は本・原本版・読書版・ブロックID・対象テキストの種別を特定する。OCR原文と修正本文のオフセットを混用しない。文字位置は0起点のUnicodeスカラー値の数、範囲は開始を含み終端を含まない`[start, end)`とする案を採る。UTF-8のバイト数、UTF-16のコード単位数、画面上の字数へ暗黙変換しない。

オフセットの対象は、その版に保存した文字列である。検索用の正規化文字列は別に持ち、引用位置へ戻す対応を保持する。クライアント側で改行・空白・結合文字を正規化してからオフセットを使わない。不正なUnicode、負数、逆転・範囲外の位置、別版のブロックを拒否する。

Swiftの`unicodeScalars`、Rustの`chars()`、Pythonの文字列で同じ範囲になるfixtureを作る。例は補助平面文字、結合濁点、絵文字の結合列、改行を含める。`A𠮷がB`では`[1,2)`が`𠮷`、`[2,4)`が結合濁点を含む`が`を指す。表示上のハイライト調整は保存位置を書き換えない。

PDFはCT-02の物理ページ番号と回転後crop box座標を使い、原本ハッシュも検証する。位置不明はnullと理由を返す。再OCR後の対応表には一対一・分割・結合・対応不明を区別し、自動移動できない記録は旧版に残す。

**契約試験:** 三言語で抽出した文字列が一致し、同じ原本ページ・領域へ戻れる。誤った版・ハッシュ・位置を拒否する。EPUBの位置形式は将来拡張として予約し、初回の対応能力に含めない。

## C-02 公開パッケージを固定する

対象: CT-01/03/04、NB-01/04/05。noteBoogieは版ごとの成果物を確定し、mangaga側アダプターが配信用パッケージを発行する。

本文を変えず音声だけ追加した場合にも使える`publication_id`を、本・原本版・読書版とは別に持つ案とする。一度発行したmanifestは不変とし、追加・修正は新しいIDで発行する。最新への参照だけを切り替え、同じIDから別内容を返さない。再送は同じ公開IDに収束させる。

| パッケージの能力 | 必須生成物 | 任意生成物 |
|---|---|---|
| 原本のみ | 原本、原本ハッシュ、本・原本版の情報 | 利用可能な書誌・品質情報 |
| 読書本文付き | 上記に加えて本文・構造・位置対応・読書版 | 章音声、要約、図のAI説明 |

原本のみの場合は読書版を未提供と明示し、RSVP可能と表示しない。本文付きでは必要な生成物が揃ってから切り替える。音声の追加取得は章単位で行い、取得対象の公開IDと音声IDを固定する。

manifestにはSchema版、公開ID、元の版、能力、品質状態、成果物ID・種類・ハッシュ・サイズ・MIME・生成元を含める。暗号化前の成果物ハッシュと暗号化後の配信ハッシュを区別し、どの段階で検証するかをSchemaに書く。暗号形式は既存Rust APIに従う。

配信側が永続保存して受領を返すまで発行イベントを再送できるようにする。本文修正と音声追加の同時発行でも、旧音声を新版の本文由来と表示しない。配信URLが期限切れなら同じ成果物IDで再取得し、別の最新版へ黙って切り替えない。

**契約試験:** 同じ公開IDの再通知、音声のみ更新、ダウンロード途中の更新、応答喪失、ハッシュ不一致、原本のみの本を検証する。旧版の取得可否はC-05の保管条件に従う。

## C-03 学びの記録を受け渡す

対象: CT-04/05、NB-06/07/09。保存済み回答の取得と削除、利用者メモの同期を共通契約に追加する。noteBoogieにある既存会話の内部IDを、そのまま新しい外部契約とみなさない。

| 記録 | 必要な対応付け |
|---|---|
| 質問・回答 | 記録ID、会話ID、要求ID、本と入力版、指定した章/ブロック、質問文、回答、回答状態、処理・モデルの識別情報 |
| 引用 | 引用元の種類、成果物と版、ブロックと範囲、引用文、原本位置。位置不明の理由も保持 |
| 利用者のメモ | メモID、対象の本/章/回答、利用者が書いた本文、編集の基準版 |
| 同期情報 | 端末ID、イベントID、記録の更新版、サーバーカーソル、削除記録 |

会話の各質問で対象範囲を照合する。履歴があることを理由に別の本・版へ範囲を広げない。再回答は新しい回答IDで保存し、元の回答を残す。引用一致の検証状態と、回答が引用で裏付けられるかという品質評価を分ける。

APIには本/章/語句による検索、カーソル付き履歴取得、記録の取得・編集・削除、書き出しを定義する。Schemaには本文長、ページサイズ、履歴の文脈上限、エラーを含める。上限超過は明示して返し、対象範囲を黙って切り詰めない。エンドポイント名は次版のOpenAPIで固定する。

生成要求の再送と、保存済み履歴の同期再送は区別する。同じ要求IDで有料生成を重複起動しない。プロバイダーへの送信後に結果が不明になったときは状態不明として照合し、盲目的に再生成しない。

オフライン質問は暗号化した下書きに留め、接続後に利用者の送信操作で実行する。端末には取得済みの回答・引用・メモを保存し、検索対象が端末内か書庫全体かを表示する。書き出しはID・版・出典・著者種別を保つJSONと閲覧用Markdownを提供し、未取得記録や欠けた参照を明示する。

**契約試験:** iPhoneで質問・追記した記録をWebで検索し、同じ引用を開いて書き出す。編集競合、古い版、再送、削除、オフラインからの復帰を含める。

## C-04 認証と復号の担当を固定する

対象: CT-04/05/06、NB-07/08。原文を扱うPCを信頼する構成を前提とする。次の担当を推奨し、鍵の保管方式はA段階で確定する。

| 境界 | 担当と条件 |
|---|---|
| iPhoneから外部入口 | mangagaが初回登録、接続先書庫の表示、端末ごとの認証・失効・再認証を扱う。noteBoogieの共有パスワードやモデルキーを渡さない |
| アダプターから内部API | アダプター専用のサービス認証を使い、対象書庫と許可操作をサーバー側で照合する。内部ポートの非公開化だけで認証を代替しない |
| PCから端末への配信 | PC上のアダプターが、利用可能な鍵と既存Rust APIで暗号化する。鍵がなければ待機する |
| 端末からの記録 | mangagaが暗号化した送信待ち記録を保管する。PC上のアダプターが既存Rust APIで復号・検証し、認証済み内部APIでnoteBoogieへ渡す |
| Webからの参照 | noteBoogieがPC上の記録を認証済みWebへ返す。PCは平文を扱えるため、PCからも内容を隠す暗号化とは説明しない |

アダプターが鍵待ちの場合は、受領済み暗号文とnoteBoogieへ反映済みの状態を区別する。記録はnoteBoogieの永続保存後に適用確認を返し、iPhoneは確認まで再送可能な状態を保つ。再送を何度受けても記録は増殖しない。

OSの資格情報保管による無人運用か、起動後の手動解錠かを選び、バックアップと鍵紛失時の復旧を試験する。パスフレーズのDB保存や独自暗号は導入しない。別プロフィール・別書庫を推測で対応付けず、端末失効時は新規APIアクセスと未完了の要求を拒否する。

**契約試験:** 初回登録、失効・再登録、鍵待ち、書庫不一致、不正ID、重複イベント、復号後の停止、適用確認の応答喪失、復元後の再接続を検証する。

## C-05 削除と再同期を定める

対象: CT-03/05/06、NB-07/09/10。保存の正本はnoteBoogie、端末の取得状態はmangagaが管理する。

初期設定では原本・利用者の記録・参照中の版を自動削除しない。費用・容量の上限に達したら新規生成を止め、削除候補と影響を提示する。旧音声や版を整理する場合も、参照中の記録、公開パッケージ、取得中の要求への影響を照合する。

端末から外す操作はPCの本を削除しない。サーバーの論理削除は削除記録として同期する。物理削除は保持条件と参照関係を確認した別操作とし、リンク先を失う記録にはその状態を明示する。復元できる期限と方法を利用者に示す。

削除記録を整理する場合は有効な同期カーソルの下限を定める。期限切れカーソルには全体の再同期が必要と返し、古い差分を新規イベントとして適用しない。端末は未送信の編集を退避してから再同期し、削除済みの本への注釈は失わず、復元するか独立したメモとして残すかを選べるようにする。

バックアップは本・版・成果物・記録・参照対応・同期状態・鍵の復旧手段を一組として扱う。復元でサーバー状態が巻き戻った場合も古いカーソルを誤って受理せず、未送信記録を保持して再同期する。保持日数・容量・カーソル期限の具体値は代表書庫の測定後、受入前に固定する。

**契約試験:** 端末だけの削除、サーバー削除、期限切れカーソル、未送信編集、参照中の版、取得中の版、バックアップ復元後の再同期を通す。

## 採用時に両側で揃える

| 追加案 | 既存契約 | 合意時に揃えるもの |
|---|---|---|
| C-01 | CT-02/05 | 位置のSchema、文字列・座標fixture、旧新対応の状態 |
| C-02 | CT-01/03/04 | 公開ID、能力別manifest、ハッシュの対象、公開イベント |
| C-03 | CT-04/05 | 履歴API、記録Schema、冪等キー、書き出し形式 |
| C-04 | CT-04/05/06 | 認証手順、書庫対応、鍵管理、書き戻しの受領/適用確認 |
| C-05 | CT-03/05/06 | 削除・復元の状態、カーソル失効、保持設定 |

契約変更は新しい版として記録する。未対応の版を拒否し、旧版の書庫を開ける移行経路と回帰試験を用意する。A段階ではB・Cに必要な契約を確定し、C-03はDの着手前までに確定する。
